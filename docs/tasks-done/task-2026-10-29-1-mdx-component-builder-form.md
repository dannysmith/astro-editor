# MDX Component Builder Form

Turn the MDX component builder into a form for inserting **new** components: a control per prop, filled with the right value syntax, so writers don't have to remember a component's options or MDX's attribute rules. Also offer Starlight's built-in components in Starlight projects. Covers #289 and #284. Editing components already in the document is out of scope; the markdown editor does that.

The value is mostly in props with a fixed set of options (literal unions, enums, icons), dates, numbers and booleans, where the form knows the options and the syntax and the writer doesn't have to.

Branch: `mdx-builder-form`.

## Decisions

- **Rust sends a structured `PropKind`** (`string`, `number`, `boolean`, `literals`, `array`, `date`, `image`, `collectionEntry`, `unknown`) alongside the source text of the type. The frontend maps each kind to a control and doesn't parse type strings.
- **Static parsing only, no type checker at runtime.** The parser resolves what a writer-facing form needs and gives up (`unknown`, a text field) on the rest.
- **Starlight's components come from a bundled manifest**, generated by a script in this repo at our build time, not read from the user's `node_modules`. The package layout already moved once (`user-components/` → `dist/user-components/`), and some props (Badge's come from a Zod schema) need a real type checker. The generator can use one because it only runs on our machines.
- **`children` is the slot, not a prop.** React and Svelte components with a `children` prop get `has_slot` and the prop is dropped from the list.
- **Starlight components are inserted exactly like project components,** including imports. Import insertion (#287) isn't on main yet: it's one commit (`f1873e3d`) on the local `2026-07-13-work` branch, behind a per-project setting that's off by default. Until it lands, no component gets an import. When it does, Starlight components need a fixed import source (`@astrojs/starlight/components`) rather than one computed from a file path, so the manifest carries `import_source`.
- **Props whose type we can't read** (`unknown`, and `image`/`collectionEntry` until #287) get a text field and are inserted as strings (`prop="…"`).
- **Optional booleans have three states:** not set, on, off. Not set leaves the prop out. Required booleans are a plain switch.
- **The Rust code lives in `src-tauri/src/mdx_components/`** (scanning and framework parsers in `mod.rs`, type resolution in `prop_types.rs`), with `commands/mdx_components.rs` as a thin command.

## Spike findings

### Spike 1: Rust prop parsing (kept, on the branch)

`src-tauri/src/mdx_components/prop_types.rs` is a small resolver on top of swc. It handles:

- local interfaces, type aliases and string enums
- `(typeof LIST)[number]` over `as const` arrays (and `readonly [...]` tuples in `.d.ts` files)
- intersections (`Own & HTMLAttributes<'span'>`), and `extends` of local interfaces
- relative imports and re-exports, followed into sibling `.ts`/`.d.ts` files inside the project
- defaults from `const { a = 'x' } = Astro.props`, React parameter destructuring, Vue `withDefaults` and destructured `defineProps`, Svelte 4 `export let` and Svelte 5 `$props()`
- JSDoc on props (before, or trailing on the same line) and the component's leading JSDoc as its description

It skips anything inherited from types it can't see (`HTMLAttributes`, `Omit<…>`), which is what we want. `.astro` frontmatter now needs whole-line `---` fences. Vue and Svelte now parse their scripts with swc rather than string matching.

Tested against real components copied into `test/mdx-components/` (danny.is's 29 and Starlight's 11). Run `cargo test fixture_tests -- --nocapture` in `src-tauri` to see everything it reads. Results:

- **danny.is:** everything resolves as expected, including defaults and JSDoc. Nothing comes out wrong. The only `unknown` is an internal helper's `TreeNode[]`.
- **Starlight via the parser:** Aside's `type` resolves through two imports to `note | tip | caution | danger` (default `note`), and `StarlightIcon` to 277 icon names. Badge gets no props (Zod-derived), which is why Starlight uses the manifest instead.
- The dummy project's components all read correctly in the running app.

Not handled: tsconfig path aliases (`@lib/x`) in type imports. Use `oxc_resolver` if real projects need it; nothing in the fixtures does for a writer-facing prop. Tuples and object types are `unknown`. Number-literal unions become `number`.

### Spike 2: Starlight manifest (throwaway script)

`scripts/spikes/starlight-manifest/generate.ts` uses the TypeScript 6 compiler API against `website/node_modules/@astrojs/starlight` and writes `docs/tasks-todo/temporary/starlight-manifest.json`. It runs in about half a second and gets all 12 components (including `Code` from Expressive Code) right, with defaults. Badge's defaults come from importing its Zod schema at generation time.

- **"Own props":** props declared anywhere outside `node_modules/astro/` are kept, which drops the 190–200 inherited HTML attributes per component. It wrongly drops LinkCard's `href` (inherited from `HTMLAttributes<'a'>`), so it needs an override.
- **Size:** 54 KB, 4.4 KB gzipped, mostly the icon list repeated in five props.
- **Literal order** comes out in the type checker's internal order, not source order (Badge's variants start with Aside's). Overrides or sorting fix it.
- **Code** needs hand-tuning: it isn't really slotted, `mark`/`ins`/`del` are `unknown`, a few props aren't for writers, and `code` is multi-line, so it must be emitted as `` code={`…`} ``.

The fragile parts: depending on astro's package path for "own props", and on Zod 4 internals for Badge's defaults. Both fail loudly when we regenerate rather than for users.

## Plan

- [x] `PropKind` and `description` on `PropInfo`, regenerated bindings
- [x] Resolver for aliases, enums, const arrays, intersections and relative imports (`prop_types.rs`)
- [x] Move the component code into `src-tauri/src/mdx_components/`
- [x] Defaults and JSDoc for all four frameworks; whole-line frontmatter fences
- [x] Fixture tests against `test/mdx-components/`
- [x] Review fixes: unions of one kind collapse (`1 | 2` is a number), the component description only comes from JSDoc up to the `Props` declaration, Vue reads `<script setup>` and Svelte skips the module script, and an Astro file that won't parse is still listed
- [x] Real-world fixtures collected into `test/mdx-components/` (see its README); `cargo test --lib dump_all_fixtures -- --ignored --nocapture` prints what each reads as
- [x] Fixes from the real-world fixtures: defaults through `Astro.props as Props`, `keyof typeof obj` and `keyof Interface` as literals, untyped destructures (`const { a, b = 2 } = Astro.props`, untyped `$props()`) listed with kinds from their defaults, Vue runtime `defineProps({ a: String })` / `defineProps(['a'])`, `URL` as a string, and mixed unions like `string | Post` as unknown rather than string
- [x] `oxc_resolver` alias support: not now. Astro Cactus is the one fixture that needs it
- [x] Enum member defaults show as the enum's value (done in the UX round)

Known limits from the fixtures, which fall back to a text field or nothing: arrays of objects (`sources: { src; type }[]`), object and discriminated-union props, props typed from another component (`Parameters<typeof Badge>[0]`) or mapped package types, defaults that live in a Zod schema or a function, and polymorphic `as` props. A lowercase file (`post.astro`) gives a lowercase component name.

### Phase 2: The form

- [x] `serializeProp` and `buildSnippet`/`buildPreview` in `lib/editor/snippet-builder.ts`, with unit tests: `prop="x"`, `prop={42}`, bare `prop` / `prop={false}`, `prop={new Date('2026-01-01')}`, `prop={['a', 'b']}`, template literals for strings with quotes or newlines, and braces escaped for CodeMirror's snippet parser
- [x] The configure step is a form (`ComponentForm`, `PropField`) in the same dialog; the component list stays a cmdk list. Controls:
  - `string`, `image`, `collectionEntry`, `unknown` → text input
  - `number` → number input
  - `boolean` → switch when required; select of (Not set) / true / false when optional
  - `literals` → select, with (Not set) when optional
  - `date` → date picker
  - `array` of literals → multi-select, kept in declared order
  - other `array`s → tag input (number arrays drop anything that isn't a number)
- [x] A prop is inserted only when it has a value, or is required. Defaults show as "Default: x" under the field, as in the frontmatter panel.
- [x] Prop descriptions as help text, the component description in the list and the form header
- [x] Keyboard: focus starts in the first field, Tab between fields, Cmd+Enter inserts, Escape goes back to the list (and closes from there)
- [x] Required props left empty become snippet tab stops
- [x] Styleguide section (`component-builder`)
- [x] Test project components covering each kind and framework pattern: `Event` (every kind), `Pricing` (types imported from a sibling file, `extends HTMLAttributes`), `Figure` (`ImageMetadata`, `CollectionEntry`), `Poll` (Svelte 5 `$props()`), `Rating` (Vue `withDefaults`), `Timeline` (React `FC<Props>`, string enum). `src/pages/components.astro` renders the Astro ones so the build checks them; a Rust test asserts what's read from them.

- [x] A searchable combobox for long literal lists (done in Phase 3)
