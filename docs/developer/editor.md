# Editor

The writing surface is vanilla CodeMirror 6 (no React wrapper), parsed by Lezer's markdown grammar. This doc covers the rules for touching `Editor.tsx`, how the editor scrolls and takes focus, how highlighting works and where it doesn't, and how edits get to disk without losing anything. Each extension in `src/lib/editor/extensions/` has a header comment explaining what it does and why; read those for detail.

## One Lezer, one CodeMirror

Only one copy of `@lezer/common` and of each `@codemirror/*` package may be installed. Lezer's `Tag` and tree objects from different versions aren't compatible, so a duplicate breaks highlighting at runtime without an error, and a duplicate `@codemirror/view` breaks typecheck. `package.json` pins `@lezer/common` with `overrides`, but `bun update` can still leave older copies nested under other packages. AGENTS.md has the check and the fix.

## Editor.tsx

`Editor.tsx` owns the `EditorView` by hand, and the store mirrors it rather than driving it:

- **The view is created once** (an effect with empty dependencies). Recreating it would lose undo history, selection and scroll.
- **Typing flows editor → store.** The update listener writes `editorContent` to the store, which marks the file dirty and schedules auto-save.
- **Everything else flows store → editor through `useEditorStore.subscribe`,** not a React subscription, so typing never re-renders the component. It's wrapped in `React.memo` with a comparator that always returns `true` for the same reason.
- **Store-to-editor writes set `isProgrammaticUpdate`** so the update listener doesn't mistake them for typing. Without it, loading a file would mark it dirty and save it straight back.
- **A store write that differs from the document replaces the whole document.** That loses the scroll position (and typewriter mode re-centres on any `docChanged`), so it should only happen when a file is opened or changed on disk. See the round trip below.
- **Loading a document starts the undo history afresh** (`loadDocument` in `lib/editor/load-document.ts`). Undo can't reach the previous file, or back across a reload from disk, where undoing an earlier edit could insert stale text.
- **Modes** (focus, typewriter, the Alt key for URL and image hover) are toggled with state effects, not by recreating extensions.

## Scrolling and focus

The editor scrolls itself: `.cm-scroller` (`view.scrollDOM`) is the scrolling element, and `MainEditor`'s container doesn't scroll. That lets CodeMirror's scroll handling work fully. It keeps the text still when lines above the view change height as they're measured, which it only does for an outer scroll container while the editor has focus. The 24px side margins are padding on `.cm-scroller`, so the scrollbar sits at the pane's edge and the margins scroll the text too.

- **Scroll with CodeMirror, not the DOM.** To scroll something into view, dispatch `EditorView.scrollIntoView` (or `scrollIntoView: true` on a transaction). Setting `scrollTop` directly is for keeping the text still when the layout changes under it, as typewriter mode does when its padding comes and goes.
- **Focus the editor with `view.focus()`** (or `focusEditor()` from `lib/focus-utils.ts`), never by focusing `.cm-content`. WebKit 26 ignores `focus({ preventScroll: true })` and scrolls to the editor's old selection, often the top of the document. CodeMirror works around it by recording the scroll positions around the focus and restoring them, but only when it knows it's in Safari 26, which is why the macOS window's user agent says so (see `cross-platform.md`).
- **Toolbar buttons don't take focus** (`TitleBarToolbar` cancels mousedown on its buttons), so clicking one leaves the cursor where it was.

## Highlighting

Highlighting runs through custom tags rather than `@lezer/highlight`'s built-in `tags.*`, so headings, emphasis and their syntax marks can be styled separately:

- `syntax/markdownTags.ts` defines the tags;
- `syntax/styleExtension.ts` maps Lezer nodes to them with `styleTags`;
- `syntax/highlightStyle.ts` maps tags to styles.

**Contextual mark rules don't fire.** Since `@lezer/highlight` 1.2.3, `@lezer/markdown`'s built-in rule (every mark → `tags.processingInstruction`) is checked before ours, so a rule like `'ATXHeading1/HeaderMark'` in `styleExtension.ts` is silently ignored. `extensions/syntax-mark-decorations.ts` works around this by walking the tree and decorating heading, emphasis and strong marks directly, and `theme.ts` gives those classes `inherit !important` to beat the inner highlight spans. Style any new contextual mark the same way.

`styleTags` also only applies to the exact node, not its children, which is why whole-blockquote styling is a line decoration (`blockquote-style.ts`).

**MDX files are parsed as MDX.** `syntax/language.ts` holds the Markdown language in a compartment, and `Editor.tsx` switches it with `setEditorLanguage` when a file opens. In an `.mdx` file, `syntax/mdx.ts` reads a line holding only JSX tags (which may span lines) as an `HTMLBlock` of just those tags, so a component's contents parse as Markdown, as MDX renders them; it also drops indented code, which MDX doesn't have. In a `.md` file CommonMark's HTML blocks stay, since Astro doesn't render Markdown inside raw HTML either. Reusing `HTMLBlock` keeps tag highlighting and Harper's masking working unchanged. MDX tags are parsed as JSX, so attribute expressions highlight, except a tag starting `</`, which JSX can't parse without its opening tag and goes to HTML.

**Code in fenced blocks** is parsed in the fence's language (`syntax/codeLanguages.ts`: `@codemirror/language-data`, loaded lazily, plus Astro as TSX and Svelte as HTML), and coloured by the standard `tags.*` rules in `highlightStyle.ts`. It's only shown highlighted in the block holding the cursor: `code-block-background.ts` adds `cm-codeblock-active` to that block's lines, and `theme.ts` resets the colour and weight of code spans in every other block. lang-markdown mounts code (and HTML) as overlay trees, which `Tree.iterate` doesn't enter, so extensions that walk the tree for Markdown nodes never see a heading or emphasis inside a ```` ```markdown ```` fence. Only the parser of a nested language is used, not its extensions, so no completions or auto-closing tags come with it.

Colours and type come from `editor-styles.md` and the `--editor-color-*` tokens in `App.css` (see `color-system.md`).

## Spelling, grammar and style checks

The Copyedit panel's checks run [Harper](https://writewithharper.com) through `@codemirror/lint`. The code is in `extensions/harper/`, and each file's header says what it does. Things to know before changing it:

- **Harper checks a masked copy of the document.** `prose.ts` replaces everything that isn't prose (code, URLs, tags, MDX) with a private-use character, keeping the document's length, so Harper's offsets are document positions. New Markdown or MDX syntax that isn't prose needs masking there, or Harper will check it.
- **Harper runs in its own worker** (`harper.worker.ts`), which answers with plain data. The main thread never loads harper.js or its WebAssembly, so don't import harper.js values outside the worker (types are fine).
- **A fix only applies while the issue covers the text it was raised on** (`issues.ts`). Checks are a second or more behind typing, so anything that edits the document from an issue has to go through `applyFix`.
- **Harper's tooltip is the editor's only hover tooltip,** so `tooltip.ts` styles `.cm-tooltip-hover` itself. The lint package's own tooltip is emptied with `tooltipFilter` but still adds an empty section, which is hidden. A new hover tooltip needs those styles scoped to Harper's section first.

## Pasting and dropping

`lib/editor/paste/` and `lib/editor/dragdrop/`. Drops come from Tauri's drag-drop event as file paths; pastes come from WebKit's `paste` event. Both save into the collection's assets through `add_to_assets` in `commands/files.rs`, which converts HEIC to JPEG (`heic.rs`), because Astro can't use it.

- **Images on the clipboard arrive as files** in `clipboardData.files`: screenshots and images from Preview as `image.png`, Photos' as a UUID-named JPEG, Finder's with their names. Copy Image in a browser also gives HTML that's only the `<img>`, which is where the alt text comes from. Their bytes cross to Rust as base64: a byte array goes through JSON as a list of numbers, about fifteen times slower, and tauri-specta can't type a raw-body command.
- **Copied rich text is converted from its HTML structure only** (`html-to-markdown.ts`). WebKit strips Word's list markup before the page sees it, so Word's lists and headings, which are only bullets, indents and fonts, paste as paragraphs. That's deliberate: guessing structure from styling is where converters grow. The test fixtures are real pastes from Safari, Chrome, TextEdit and Word.
- **⇧⌘V (paste as plain text) gets no paste event** from WebKit, so it reads the clipboard through the clipboard plugin in Rust; `navigator.clipboard.readText()` would show a permission prompt.
- **`sips` exits 0 when it can't reach the HEVC decoder** (in a sandbox, like an AI agent's), having written a JPEG with no pixels, so the result is checked. The tests that convert a real HEIC are `#[ignore]`d for that reason; run them with `cargo test heic -- --ignored`.

## Auto-save and data safety

Never losing work is a product principle, and each of these rules guards against a way of losing it.

- **When it saves:** `scheduleAutoSave` in `editorStore.ts` debounces by the `autoSaveDelay` setting (2 seconds by default). Debouncing alone never fires during continuous typing, so a save is also forced once the first unsaved edit is 10 seconds old (`dirtySince`, `MAX_AUTO_SAVE_DELAY_MS`). The clock starts at that edit, not the last save: timed from the save, the first keystroke after a pause would be saved on its own, which writes half-typed frontmatter values. A forced save restarts the clock, or every keystroke until it finished would fire another.
- **Who saves:** the store can't call hooks, so Layout registers `useEditorActions().saveFile` as the store's auto-save callback (the Hybrid Action Hooks pattern, see `architecture-guide.md`). Auto-save never shows the success toast (it saves with `showToast` false); a failed save still shows an error.
- **AE never reads an entry while it's saving one** (`ENTRY_IO` in `commands/files.rs`, held by `parse_markdown_content` and `save_markdown_content`). Writing in place empties the file first, and AE reloads the open entry after every save, which can overlap the next save (Cmd+S during an auto-save). A reload landing mid-write would put an empty or half-written entry in the editor, and the next save would write that back.
- **Editing pauses while git rewrites files** (`editingPaused` in the editor store, set by the Git tab's Pull before it saves the entry). Otherwise anything edited during a pull would keep the old text and then save it over the pulled changes. The store ignores body, frontmatter and import edits. The editor is read-only, which only stops typing, so a change filter (`lib/editor/editability.ts`) refuses every other change too (formatting commands, drops, pastes, fixes), apart from a file load (`fileLoad`). The filter is in a compartment and only there while paused, so it costs typing nothing.
- **Saves write in the order they were asked for.** Saves can overlap (Cmd+S during an auto-save), so each disk write waits for the one before (`lib/files/write-queue.ts`) and an older one can't land last. Reads of an entry wait for that queue too, so reopening a file during a save can't load the text from before it. Each save still reads the store when it's asked for, which switching files relies on.
- **Saves write the file in place,** not to a temporary file renamed over it. An editor should write the file itself, as VS Code does, so it keeps its inode, and with it hard links, permissions and anything watching it. Files with CRLF line endings are written back with LF: CodeMirror and `parse_frontmatter` both normalise them.
- **Switching files saves first.** `openFile` runs the save for a dirty file before replacing the store's state. A save that finishes after the switch only updates the store if the file hasn't been opened or closed since (`openGeneration`, which a rename doesn't change). Comparing paths wouldn't do: after switching away and back, the store holds the same path with an unloaded placeholder, and the save would take that for new edits. If the save fails, the recovery data is the outgoing file's.
- **Opening the open file keeps it as it is.** Loading it again would lose its undo history, cursor and any unsaved edits, so `openFile` only checks a clean file against disk.
- **Closing a file saves first.** `editorStore.closeFile` (Close File, Ctrl+W on Windows and Linux) saves a dirty file and leaves it open if the save fails. `closeCurrentFile` is the plain reset, for callers that have saved already or whose file is gone.
- **Deleting the open file closes it without saving** (`lib/files/delete.ts`), since the next save would write it back.
- **Async inserts check the file is still open.** An image drop copies the image before inserting its path, and the component builder plans imports before inserting; if another file was opened meanwhile, the insert is dropped rather than put in the wrong file.
- **Quitting saves first.** Every way of quitting (Cmd+Q, the Dock, logout and shutdown on macOS; closing the window or Exit on Windows and Linux) makes Rust emit `quit-requested` instead of exiting. `answerQuitRequest` in `lib/quit.ts` saves the open file and calls `quit_app`. If the save fails it calls `cancel_quit` and asks whether to quit anyway, since recovery files can't be restored from the app. Rust quits by itself if the frontend doesn't answer within 5 seconds, so a hung webview can't make the app unquittable. Restarting to install an update calls `saveUnsavedEdits` first too. The Rust side, including the macOS hook, is `src-tauri/src/commands/quit.rs`.
- **Renaming the open file never leaves a copy behind,** whether it's renamed from its pattern (`renameOpenFile`) or in the sidebar (`renameFile`), both in `lib/files/rename.ts`. A dirty file is saved first, and the rename is given up if that fails or another file was opened meanwhile. While Rust renames it, a save of the old path waits (`renameUnderWay`) and then writes to the new one, since writing to the old path would bring the old file back. The store gets the new path as soon as the rename is done, then the file's new id. Renames never replace another file: `rename_file` and `rename_entry` refuse if the new name is taken, except by the same file with a change of case.
- **An opened file is always read from disk.** File content is cached by the file's path, and a file is identified by its path everywhere in the editor. Its `id` is the Astro entry id, which leaves out the extension, so `post.md` and `post.mdx` share one and treating them as one file overwrites one with the other. A path can still be reused: renaming or deleting a file frees it for another file. So `openFile`, and following a rename onto a new path, drop the cached content for that file first. Otherwise a file created with ⌘N right after the last new file was renamed would show that file's title, since both started as `<today>.md`.
- **Nothing edits or saves a file before it has loaded.** From `openFile` until its content arrives, the store holds an empty placeholder, and saving it would write the placeholder over the file. So until `isLoaded` is set, the editor is read-only, the store's edit actions do nothing, and `saveFile` writes nothing. A file that can't be loaded shows an error in place of the editor, which stays mounted. The file content query doesn't retry: a file that can't be read fails the same way every time.
- **The frontmatter panel holds its values while the next file loads.** Within a collection the fields are the same, so blanking them for the moment a load takes makes the panel flicker and jump. `openFile` keeps the outgoing values in `heldFrontmatter`, and the panel reads through `shownFrontmatter` and `shownFilePath`, which change to the new file in one update. They're for display only. `frontmatter` still empties at once, because saves, renames, the Git tab and recovery all read it and must never see one file's values against another. Anything in the panel that acts on the file it shows has to wait for the load (`RenameToDateLink`, `ImagePicker`).
- **Frontmatter is found and read as Astro does.** `find_block` (`src-tauri/src/frontmatter/mod.rs`) takes the block between `---` lines at the top of the file, after an optional byte order mark and blank lines, with spaces allowed after the fences. An opening `---` that's never closed is a thematic break, so the file has no frontmatter. TOML between `+++` fences isn't read. The YAML is read by `src-tauri/src/yaml.rs`, which matches Astro 7, so duplicate keys make frontmatter unreadable, as they fail Astro's build. `test/frontmatter/README.md` lists the few differences from Astro and how to compare with it.
- **Frontmatter that can't be read is kept as text.** When the YAML doesn't parse, `parse_markdown_content` still returns the body, the imports and the raw frontmatter, with the parser's error (`frontmatter_error`, its line numbers counted from the top of the file). The body can be edited; the frontmatter panel shows the error, the store ignores frontmatter edits, and saving writes the raw text back unchanged.
- **Edits during a save survive.** After writing, `saveFile` marks the file clean only if the content and frontmatter in the store still match what it wrote. Anything typed while the save was in flight stays dirty and is saved next time.
- **Edits keep the user's YAML.** If the frontmatter wasn't touched (`isFrontmatterDirty`), the block on disk (`rawFrontmatter`) is written back unchanged. An edited frontmatter's values are spliced into the text it was loaded from (`write_block` in `src-tauri/src/frontmatter/write.rs`): keys whose values didn't change keep their text and comments, including inside a nested object written as a block (a list of objects or an inline object is rewritten whole), changed keys are written in the style of their old text and the rest of the block (quotes, inline lists, indentation, a trailing comment), and new keys go at their schema position. With the project's "Reorder frontmatter" setting on and the collection's whole schema known, keys are put in schema order, then the rest alphabetically, each with its text and comments. A date-like string is written unquoted, so Astro reads it as a date, only in a date field or where it was unquoted before; everywhere else it's quoted.
- **What's written must read back as what was saved.** `write_block` reads its result back and compares it with the values. If the splice doesn't match (an alias to another key's anchor can't be split off, for one), the whole block is written from the values; if that doesn't match either, the save fails and nothing is written, so the file stays dirty and recovery data is written. Values come back from JavaScript, so numbers are compared by value (`1.0` is `1`, and an integer too big for JavaScript to hold exactly is unchanged by the rounding).
- **Edits are spliced into the baseline, not the last save.** The first load after opening a file is kept as its `frontmatterBaseline` (values and text, `lib/files/frontmatter-baseline.ts`), and every save of edited frontmatter splices into the baseline's text. So the file only ever differs from the baseline by the edits, however many auto-saves came between: a key cleared and retyped goes back where it was with its comment, and the quotes a half-typed value needed (`"Hello "`) don't stick. A save whose values are back to the baseline's writes the baseline's text as it is, so a field changed and changed back, or a switch turned on and off again, leaves the file as it was. The save returns the block it wrote, which becomes `rawFrontmatter`; a load whose frontmatter is anything else was changed outside the app, and becomes the new baseline.
- **Unsaved edits win over disk.** When the file content query refetches, `useEditorFileContent` only copies it into the store if the file isn't dirty, and the read isn't from before the last save, which would bring back older text.
- **A clean file always follows disk.** `useFileChangeHandler` re-reads the open file on every watcher event unless it's dirty. Events from our own saves are never filtered out by time, since an outside change landing just after a save would be missed and then overwritten by the next one. Such an event reads back the same text, so the editor isn't touched. For 3 seconds after a save, events for the open file don't refresh the file lists, because one save can produce several events. Every other watcher event refreshes the sidebar and entry pickers, so files added, renamed or edited outside the app show up. Our own saves re-read the collection's listings only once the frontmatter has been edited; a body-only save just updates the file's modified time in the cached listing, since re-reading a large folder on every auto-save is slow.
- **The save round trip must be byte-identical.** After a save, the content query refetches the file. If parsing it back gives even slightly different text than the editor holds, the store write replaces the whole document and the view jumps every few seconds as auto-save runs. A trailing newline added by the save and dropped by the parser is enough. The round-trip tests in `src-tauri/src/frontmatter/` (`saved_bodies_read_back_exactly`, and the corpus tests over `test/frontmatter/` and `test/mdx-imports/`) cover it; any change to parsing or serialising must keep them passing.
- **MDX imports are hidden, not edited.** `parse_frontmatter` splits an MDX file into frontmatter, the ESM block (its `import` and `export` statements) and the body. Only the body reaches the editor. `src-tauri/src/mdx_esm/` finds where the block ends by parsing it with swc, the way MDX does, and the block is written back as read. A block that ends in the wrong place either hides text the writer can't then edit or shows code in the editor, so check any change against the corpus snapshot in `test/mdx-imports/files/blocks.txt`.
- **If a save fails,** the file stays dirty and recovery files are written (see `app-data.md`). There's no crash recovery.
