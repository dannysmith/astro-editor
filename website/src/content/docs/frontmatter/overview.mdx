The **Frontmatter** tab in the right sidebar automatically generates a form based on your Astro content collection schema and the frontmatter present in the file. This means you get appropriate input types and a clean editing experience without any manual configuration.

![The frontmatter panel showing a generated form with fields for a post's metadata](../../../assets/frontmatter-sidebar-overview.png)

## How Schema Parsing Works

To build the form, Astro Editor needs to understand your collection's schema. It reads that schema from two places and combines them.

### 1. The generated JSON schema

When Astro runs [`astro sync`](https://docs.astro.build/en/reference/cli-reference/#astro-sync) (which `astro dev` and `astro build` also do), it writes a JSON schema for each collection into `.astro/collections/`, such as `.astro/collections/blog.schema.json`. This is where Astro Editor gets almost everything the form needs: each field's type, constraints, description and default, and which fields are required. Astro Editor watches this folder, so the form updates whenever the files are written again.

### 2. Your content config, for images and references

A JSON schema can't tell an `image()` field or a `reference()` field from plain text, so Astro Editor also reads your content config to find those two helpers. Everything else comes from the JSON schema.

```ts title="src/content.config.ts" {5,6}
const blog = defineCollection({
  schema: ({ image }) =>
    z.object({
      title: z.string().max(100), // from the JSON schema
      cover: image(), // found in the config: an image picker
      author: reference('authors'), // found in the config: an entry picker
    }),
})
```

See [Field Types](/frontmatter/field-types/) for the control each field gets.

### When there's no JSON schema

If the generated JSON schema is missing or can't be read, Astro Editor only knows the `image()` and `reference()` fields it found in your config, and treats them as optional. Every other field in a file is shown without its type, default or required marker, as plain text, a tag field for a list of text, or JSON for an object or other list. A schema imported from another file, like Starlight's, gives nothing without the JSON schema.

To fix it, run `astro sync` (or start your dev server) in your project. Astro Editor picks up the new schema on its own. The **Schema** section of the collection's page in [Project Settings](/project-settings/#schema) shows exactly what was read, and the top of the page says if the schema is missing or couldn't be read.

## Field Order and Defaults

Fields appear in the sidebar in the order they're defined in your schema, except the title field, which is always shown first.

A new file gets a placeholder title and today's date for its published date. A required switch, date or list gets off, today or an empty list. Other required fields, like text, numbers, choices and images, are left for you to fill in: they're marked required in the panel, and Astro's build names any that are still missing. If the collection has a [template](/file-management/templates/), the file starts with the template's frontmatter, and only its published date and the required fields it leaves out are filled in.

## How Edits Are Saved

Astro Editor changes only what you edit. Every other field keeps its text, comments included, and the field you changed is written the way it was before, such as in single quotes or as a `[a, b]` list. A new field goes where your schema puts it. Changing a field and changing it back leaves the file as it was. [How YAML is Handled](/reference/yaml/) has the details.

To have edited files put their fields in your schema's order instead, turn on [Reorder frontmatter](/project-settings/#content) in Project Settings.

## Frontmatter Astro Editor Can't Read

Astro Editor reads frontmatter the way Astro does, so if your site builds, its files open here. If a file's frontmatter isn't valid YAML, or has the same field twice, the sidebar says it couldn't read it and shows the error with its line number. You can still edit the rest of the file, and saving leaves the frontmatter exactly as it was. Fix it in another editor (**Open in IDE**, if you've set one in Preferences) and the fields appear.

## Fields not in your schema

Frontmatter fields that aren't part of the schema are never discarded. They're still shown in the sidebar — below the schema fields and sorted alphabetically — and they're kept when you save. Because there's no schema to describe them, they're shown as plain text inputs (a list of text values becomes a tag field, and an object or any other list is edited as JSON), rather than as typed controls like date pickers or toggles.
